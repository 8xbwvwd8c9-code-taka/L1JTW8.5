# 過安定防具：850 原生控制與施作規格

## 1. 目標與邊界

以 850 原生強化流程為唯一權威，建立防具獨立 DB 控制與可調整的強化上限，預設最高 +15。381 只提供規則數值，不覆蓋或照抄 850 核心。

第一階段只實作控制 DB、強化上限、資料載入、測試與回滾；不修改防禦、AC、物理／魔法減傷、HP、MP、成功率或其他戰鬥公式。

## 2. 已確認來源

| 1 | 0 | 0 | 20 | 0 |
| 2 | 1 | 1 | 50 | 0 |
| 3 | 2 | 2 | 75 | 0 |

850 已由 `armor.safenchant` 保存安定值，`Enchant.c(...)` 控制一般防具強化；目前沒有一般防具全域固定上限。

## 3. DB 控制

建立 singleton 表 `over_safe_armor_control`：

| 欄位 | 型別 | 規則 |
|---|---|---|
| `id` | TINYINT | 主鍵，固定 1 |
| `mode` | TINYINT | 預設 0；0=關閉、1=單階、2=累加 |
| `max_enchant_level` | INT | 預設 15 |
| `updated_at` | TIMESTAMP | 最後修改時間 |

- `mode` 非 0、1、2 時，額外能力保持關閉並記錄錯誤。
- 強化上限獨立於 `mode`；`mode=0` 仍執行最高強化限制。
- 控制列缺失、讀取失敗或 `max_enchant_level < 0` 時，採安全預設 15 並記錄錯誤。
- 安定值已高於控制上限的既有裝備不降級、不刪除，但不得再提升。

建立 `over_safe_armor_rule` 保存六筆 381 規則。第一階段只匯入、校驗，不接入角色能力。

## 4. 核心上限

```text
projectedEnchant = currentEnchant + actualAddLevel
允許條件：projectedEnchant <= max_enchant_level
```

- 普通、祝福及其他多級強化都必須檢查實際預定結果。
- 上限判定必須發生在扣卷軸、更新裝備、廣播及成功紀錄之前。
- 拒絕時不得消耗卷軸或改變裝備。
- 詛咒、降級、失敗與破壞流程不受最高上限阻擋。

## 5. 後續能力規則

後續階段使用 `overLevel = max(0, enchant - safeEnchant)`：

- `mode=0`：零能力。
- `mode=1`：只取當前 Level 單筆值。
- `mode=2`：累加 Level 1 至當前 Level。
- 超過規則表最高 Level 時不推算；必須先由 DB 新增對應 Level。
- 第一階段不得把規則套入 `L1EquipmentSlot`。

## 6. 第一階段施作項目

- 建立 install／rollback SQL、控制表、規則表及六筆來源資料。
- 建立 850 原生控制載入器。
- 在所有一般防具強化成功入口前驗證預定結果。
- 驗證普通、祝福、多級、+14→+15、+15 拒絕、降級及失敗流程。
- 更新 manifest、驗證報告與首頁紀錄。

## 7. 驗收標準

- 預設 `mode=0, max_enchant_level=15`。
- +14 防具可增加 1 到 +15；+15 不可再增加。
- 任何會超過上限的多級強化在扣卷軸前拒絕。
- DB 修改上限後可由 850 原生載入／重載流程取得。
- 三種 mode 可正確解析，但第一階段不改變角色能力。
- 武器強化、屬性強化、其他物品與戰鬥結果無回歸。
- SQL 可安裝、回滾；850 編譯沒有新增錯誤。
- 獨立套件只收本項目 Java/class、DB、控制、文件與驗證證據。
