## 原因

Clan watch 建立與解除原本以雙方各自 RAM mutation + 各自 `ClanTable.b(...)` UPDATE 的方式持久化。兩個 clan row 並不在同一 transaction 中，因此第二次 UPDATE、連線或持久化若失敗，可能留下單邊 watch 關係，造成 DB 與 RAM 不對稱。

## 解決方法

新增 `updateWatchRelationAtomic(left, right, add)`，將雙向關係收斂成單一 transaction：

1. 驗證兩個 clan 有效且不同。
2. 依 clan id 穩定排序，避免雙方同時操作時鎖序不一致。
3. 驗證 `clan_data` 為 InnoDB。
4. `setAutoCommit(false)`。
5. 使用 `SELECT clan_id, watch_clanid ... ORDER BY clan_id FOR UPDATE` 鎖定雙方 row。
6. 解析雙方 watch set；新增時雙方都先做容量上限檢查。
7. 在同一 connection 內更新雙方 `watch_clanid`；任一 UPDATE affectedRows != 1 即失敗。
8. 兩邊成功後才 `commit()`；任一例外執行 `rollback()`。
9. DB commit 成功後才同步雙方 RAM watch set 並由 caller broadcast。
10. 建立與解除都委派至同一 bilateral helper，不再保留 RAM-first/two-save 路徑。

## 安全邊界

- 缺少任一 clan row：FAIL CLOSED
- 非 InnoDB：FAIL CLOSED
- 任一 row update 失敗：ROLLBACK
- 新增任一方已達 watch 上限：FAIL CLOSED
- commit 前不得發布 RAM/broadcast state
- 保留 BUG-850-211 的 crown/actual leader authority gate
