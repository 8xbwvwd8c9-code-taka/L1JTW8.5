## BUG-850-003 — packet header EOF validation checks only the second header byte

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **MEDIUM**  
Original source identity: `ClientThread.java`  
Recovered file: `recovered-src-obf/bj/d.java`

### Evidence

Packet receive code performs:

1. `hiByte = input.read()`
2. `loByte = input.read()`
3. checks only `loByte < 0`
4. calculates packet length using both values.

There is no matching `hiByte < 0` check before the length calculation.

### Impact

A connection closing between the first and second stage of header processing can enter length calculation with an invalid first-byte value. Exact runtime effect depends on socket timing and the second read result.

### Confidence note

This is a source-level boundary defect visible in the recovered method, but it has not yet been reproduced from the supplied runtime logs.

**Not fixed.**

## BUG-850-005 — login password block count is trusted before indexing a fixed 128-byte buffer

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH for connection robustness**  
Original source identity: `C_Login.java`  
Recovered file: `recovered-src-obf/aj/be.java`

### Evidence

The login handler:

- reads a client-controlled `pwLenth`;
- decrypts a fixed 128-byte password block;
- later indexes it as `pw[(i << 2) + j]` while iterating up to `pwLenth`.

No local range check constrains `pwLenth` to the number of 4-byte words available in the 128-byte buffer before those accesses.

### Impact

A malformed login packet can drive array indexing outside the decrypted password buffer. Because the packet constructor is invoked from the packet-dispatch / ClientThread path, the resulting exception can terminate that connection.

### Confidence note

The exact malformed packet has not been replayed in the supplied runtime logs, but the fixed-size buffer and unchecked loop bound are directly visible in the recovered source.

**Not fixed.**

## BUG-850-014 — ShopWorld accepts negative purchase quantity/price and can increase account shop currency

## BUG-850-032 — ShopWorld claim persists player item before deleting the pending-claim row

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH — economic / persistence integrity under DB failure**  
Original source identities: `C_ShopWorld.java`, `ShopWorldTable.java`, `L1PcInventory.java`  
Recovered files: `recovered-src-obf/aj/cd.java`, `recovered-src-obf/ao/bd.java`, `recovered-src-obf/au/g.java`

### Evidence

ShopWorld claim action `10` performs the operations in this order:

1. read a pending item from the in-memory `character_shop` representation;
2. add it to the player inventory;
3. the player inventory path attempts to persist that item into `character_items`;
4. only afterward call `ShopWorldTable.remove(account,index)`.

The ShopWorld removal routine removes the in-memory entry first and then executes:

`DELETE FROM character_shop WHERE acc_name=? AND indexid=?`

## BUG-850-093 — character reset handler accepts reset-stage stat updates without verifying reset-mode state

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH — character attribute integrity**  
Original source identity: `C_CharReset.java`  
Recovered files: `recovered-src-obf/aj/s.java`, `recovered-src-obf/ap/u.java`

### Evidence

`L1PcInstance` has an explicit `isInCharReset` state exposed through `cv()/s(boolean)`.

However, `C_CharReset` only checks that the active character exists.

It does not verify the reset-mode flag before processing stage 1, stage 2, or stage 3.

Stage 1 accepts six client-supplied stat bytes and directly adjusts the character's STR/INT/WIS/DEX/CON/CHA to those values.

Stage 3 likewise accepts six client-supplied stat bytes and directly applies deltas to the current stats.

The handler contains no complete server-side validation of:

- reset mode authorization;
- class-specific minimum/base stats;
- total stat-point budget;
- valid final stat distribution.

### Impact

The character-reset packet path trusts client-supplied attribute values without an explicit server-side reset-state gate or full budget validation in this handler.

This is a server-authoritative character-stat integrity defect.

### Safety note

This audit records the missing validation boundary only. No packet construction or abuse procedure is provided.

**Not fixed.**

## BUG-850-094 — high-id learned skills can reach a null skill executor

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH — skill-use/session robustness**  
Original source identities: `C_UseSkill.java`, `L1AddSkill.java`, skill-executor registry  
Recovered files: `recovered-src-obf/aj/cr.java`, `recovered-src-obf/al/c.java`, `recovered-src-obf/bi/g.java`

### Evidence

The skill-executor registry returns concrete executors only for its hard-coded mapped ids and returns `null` for every other id.

Its mappings stop in the low 200s.

Separately, the server's own `L1AddSkill` logic explicitly loads and grants high-id skills:

- warrior path: skills `601..608` except `604`;
- another class path: skill `609`.

This code dereferences the corresponding SkillsTable definitions, showing these ids are expected by the server-side content model.

`C_UseSkill`:

1. derives a skill id from the client request;
2. checks that the character has learned that skill;
3. dereferences the SkillsTable record;
4. obtains the executor from the registry;
5. calls the executor without a null check.

Therefore a learned high-id skill accepted by the first checks reaches a `null` executor.

### Impact

Attempting to use one of these learned but unmapped high-id skills can raise a null-pointer exception in the skill packet handler instead of being rejected safely.

### Relation to prior finding

This upgrades the generic executor concern from `RISK-850-084` with concrete server-side high-id skill evidence.

`RISK-850-084` should be considered superseded by this finding for ids `601..609`.

**Not fixed.**

## BUG-850-095 — clan kick clears authoritative character state before clan_members DELETE succeeds

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH — clan membership persistence consistency**  
Original source identities: `C_BanClan.java`, `ClanMembersTable.java`  
Recovered files: `recovered-src-obf/aj/h.java`, `recovered-src-obf/ao/p.java`

### Evidence

When a clan leader removes a member, the handler:

1. clears the target character's ClanID/name/rank;
2. saves the character;
3. removes the character from the clan's in-memory member list;
4. then deletes the target's `clan_members` row.

The `clan_members` DELETE catches/logs SQL failure and returns normally.

No rollback restores the target character's clan state or RAM membership if that DELETE fails.

The same ordering is used for online and restored/offline targets.

### Impact

A kicked player can be fully removed from authoritative character/RAM clan state while a stale `clan_members` row remains in persistent storage.

This is the forced-removal counterpart of the leave-clan consistency defect.

**Not fixed.**

## RISK-850-098 — master/disciple relationship state depends on a global in-memory index rebuilt from characters.MasterID

Status: **STATIC_STATE_CONSISTENCY_RISK**  
Severity: **MEDIUM — mentor relationship availability/consistency**  
Original source identity: `L1Master.java`  
Recovered file: `recovered-src-obf/aq/x.java`

### Evidence

The mentor system builds a global in-memory master-to-disciple map by scanning the `characters.MasterID` column at startup.

Subsequent relationship operations mutate both:

- character `MasterID` fields; and
- the independent global in-memory map.

Some offline cleanup paths update the DB directly by character name, while online paths mutate the live character and call the normal character save routine.

The map itself is not rebuilt or transactionally coordinated with each character DB write.

### Impact

A failed character update or interrupted mentor unlink/link operation can leave the live mentor index disagreeing with persisted `MasterID` values until restart/rebuild.

### Confidence note

This round confirms the split state model and non-transactional update pattern, but not a specific deterministic player-visible failure sequence. Keep as a risk.

**Not fixed.**

## BUG-850-099 — deleting a master character does not clear disciples' characters.MasterID references

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **MEDIUM/HIGH — persistent mentor relationship integrity**  
Original source identities: `CharacterTable.java`, `L1Master.java`  
Recovered files: `recovered-src-obf/ao/o.java`, `recovered-src-obf/aq/x.java`

### Evidence

Character deletion removes the target character and several dependent-table rows, but it does not execute any reverse update such as:

`UPDATE characters SET MasterID=0 WHERE MasterID=?`.

`L1Master` rebuilds its mentor index at startup by scanning every character row.

Any row with `MasterID > 0` is treated as a disciple and inserted into the in-memory map keyed by that master object id.

The rebuild does not require that a character row for that master id still exists.

### Impact

Deleting a master can leave every disciple persistently pointing to a non-existent character object id.

After restart, the mentor subsystem reconstructs those orphan relationships instead of repairing them.

Operations that later need the deleted master's character/name can therefore observe missing or inconsistent mentor state.

**Not fixed.**

## BUG-850-100 — deleting a married character does not clear the surviving partner's PartnerID

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **MEDIUM/HIGH — persistent relationship integrity**  
Original source identities: `CharacterTable.java`, `C_Attr.java`  
Recovered files: `recovered-src-obf/ao/o.java`, `recovered-src-obf/aj/f.java`

### Evidence

Marriage is stored directly in each character row through `PartnerID`.

Marriage acceptance writes each side's partner object id into the two characters.

Character deletion removes the deleted character row, but the delete routine does not update any surviving character whose `PartnerID` references the deleted character's object id.

No reverse cleanup is performed before the target row is deleted.

### Impact

The surviving partner can remain persistently linked to an object id that no longer exists.

The stale relationship survives restart because it is stored in the remaining `characters` row.

**Not fixed.**
