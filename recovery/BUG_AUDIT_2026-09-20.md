## BUG-850-001 — GM command parameter underflow can reach ClientThread disconnect path

Status: **CONFIRMED_RUNTIME**  
Severity: **HIGH for GM/admin session stability**  
Original source identity: `GMCommands.java`  
Recovered file: `recovered-src-obf/ai/b.java`

### Evidence

Runtime log contains:

- `java.util.NoSuchElementException`
- `ai.b.a(GMCommands.java:103)`
- caller chain continues through:
  - `L1Chat.java`
  - `C_ProtoBuffers.java`
  - `PacketHandler.java`
  - `ClientThread.java`

Recovered command parsing contains several direct `StringTokenizer.nextToken()` calls with no preceding token-count validation, including built-in commands `1`, `ca`, and `4`.

`ClientThread.run()` catches propagated `Exception` and calls connection cleanup.

### Impact

Malformed or incomplete GM commands can throw before normal command handling completes and can terminate the current admin client connection.

### Note

Observed in `data/log/exception-0-0.log`.  
**Not fixed.**

## BUG-850-003 — packet header EOF validation checks only the second header byte

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **MEDIUM**  
Original source identity: `ClientThread.java`  
Recovered file: `recovered-src-obf/bj/d.java`

### Evidence

Packet receive code performs:

1. `hiByte = input.read()`
2. `loByte = input.read()`
3. checks only `loByte < 0`
4. calculates packet length using both values.

There is no matching `hiByte < 0` check before the length calculation.

### Impact

A connection closing between the first and second stage of header processing can enter length calculation with an invalid first-byte value. Exact runtime effect depends on socket timing and the second read result.

### Confidence note

This is a source-level boundary defect visible in the recovered method, but it has not yet been reproduced from the supplied runtime logs.

**Not fixed.**

## RISK-850-004 — DB pool configuration permits unbounded waiting/retry behavior

Status: **STATIC_RISK — VERIFY_AT_RUNTIME**  
Severity: **HIGH if DB becomes unavailable**  
Original source identity: `DatabaseFactory.java`  
Recovered file: `recovered-src-obf/l1j/server/b.java`

### Evidence

Recovered pool setup combines:

- `setAcquireRetryAttempts(0)`
- `setCheckoutTimeout(0)`
- `setBreakAfterAcquireFailure(false)`

and the server immediately requests a connection during initialization.

A supplied runtime log already shows DB initialization failure caused by invalid DB authentication.

### Impact

The combination is a resilience risk: DB failure/recovery scenarios may block or retry for an unbounded period depending on c3p0 runtime semantics/version.

### Confidence note

The supplied log confirms DB initialization failure handling is active, but does **not** prove an infinite wait occurred. Keep this item classified as a risk until reproduced.

**Not fixed.**
