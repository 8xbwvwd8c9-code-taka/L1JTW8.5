Severity: **MEDIUM**  
Original source identity: `ClientThread.java`  
Recovered file: `recovered-src-obf/bj/d.java`

## BUG-850-005 — login password block count is trusted before indexing a fixed 128-byte buffer

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH for connection robustness**  
Original source identity: `C_Login.java`  
Recovered file: `recovered-src-obf/aj/be.java`

### Evidence

The login handler:

- reads a client-controlled `pwLenth`;
- decrypts a fixed 128-byte password block;
- later indexes it as `pw[(i << 2) + j]` while iterating up to `pwLenth`.

No local range check constrains `pwLenth` to the number of 4-byte words available in the 128-byte buffer before those accesses.

### Impact

A malformed login packet can drive array indexing outside the decrypted password buffer. Because the packet constructor is invoked from the packet-dispatch / ClientThread path, the resulting exception can terminate that connection.

### Confidence note

The exact malformed packet has not been replayed in the supplied runtime logs, but the fixed-size buffer and unchecked loop bound are directly visible in the recovered source.

**Not fixed.**

## BUG-850-014 — ShopWorld accepts negative purchase quantity/price and can increase account shop currency

Recovered files: `recovered-src-obf/aj/cd.java`, `recovered-src-obf/ao/bd.java`

## RISK-850-168 — caster-dependent effect workers can receive a null owner from the generic effect-spawn API

Original source identities: `L1SpawnEffect.java`, `L1EffectInstance.java`  
Recovered files: `recovered-src-obf/aq/ai.java`, `recovered-src-obf/ap/h.java`

### 2026-09-21 caller follow-up

Targeted production-caller tracing narrowed the reachability question:

- player skill 58 / firewall creates gfx `168` through the owner-preserving helper; the helper ultimately calls the seven-argument spawn routine with the casting player as `user`;

- additional ownerless effect callers found in player skills (for example visual/control effects such as gfx `4184` and skill-specific gfx) likewise do not by themselves prove reachability of the unsafe firewall/cube owner assumptions.

Result: ownerless spawn is confirmed production-reachable, but no production caller has yet been proven to pair the ownerless overload with gfx `168 / 6706 / 6712 / 6718 / 6724`. Keep this finding as **RISK**, not BUG.

Original source identity: `SoulTowerTable.java`  
Recovered file: `recovered-src-obf/ao/bf.java`

### Evidence

Whenever a new result qualifies, the persistence path first executes:

`DELETE FROM soul_tower WHERE rank > 0`

and then performs up to ten separate `INSERT INTO soul_tower ...` statements in a loop.

There is no transaction spanning the delete and replacement inserts.

Any `SQLException` in the delete/rebuild block is caught and logged, after which the operation exits without rollback. The in-memory ranking list has already been updated and sorted before this DB rewrite starts.

### Impact

A DB failure after the delete, or part-way through the insert loop, can leave the durable leaderboard empty or partially reconstructed while the running process still holds the full live ranking list.

A later restart then loads only the truncated durable state. This is a directly proven RAM/DB snapshot divergence for the Soul Tower subsystem.

### Confidence boundary

The divergence requires a database failure; no claim is made that an ordinary player can directly cause that failure.

**Not fixed — audit-only mode.**

## BUG-850-252 — malformed existing character_mobs_week rows cannot self-heal because login fallback uses INSERT against a primary-key row that already exists

Tier: **L2 — Major**  
Status: **STATIC_HIGH_CONFIDENCE / REPEATABLE PERSISTENCE-RECOVERY FAILURE**  
Severity: **MEDIUM/HIGH — weekly progression state remains permanently unrecoverable until DB repair**  
Original source identities: `C_LoginToServer.java`, `CharacterMobsWeekTable.java`  
Recovered files: `recovered-src-obf/aj/bf.java`, `recovered-src-obf/ao/n.java`, bundled `db/8.5.sql`

### Evidence

The weekly-mob loader reads four comma-separated persisted columns:

- `numbers`;
- `counts`;
- `kills`;
- `states`.

It requires at least nine `numbers` entries, then indexes all four arrays using `numbers.length` without first proving the other three arrays have the same length. Any malformed/stale row with too few numbers, a shorter companion column, or unparsable numeric content exits without assigning `pc.dY()`.

The login flow then sees `pc.dY() == null`, creates the default weekly-mob state in RAM, and calls the table's create routine.

That create routine always performs:

`INSERT INTO character_mobs_week ...`

The bundled schema defines `login` as the table's PRIMARY KEY. When the malformed row already exists, this fallback INSERT cannot replace it. The insert helper catches/logs `SQLException` and returns normally.

### Impact

A stale or malformed persisted weekly-mob row becomes sticky:

1. every login fails to parse the same existing row;
2. the player receives only a fresh in-memory default state for that session;
3. the attempted repair INSERT collides with the existing primary-key row;
4. the failure is swallowed;
5. the next login repeats the same cycle.

The subsystem therefore cannot self-recover from a malformed existing row even though the login path explicitly attempts fallback initialization.

### Confidence boundary

This requires a stale/corrupt/incompatible persisted row; no claim is made that an ordinary client can directly create malformed DB text through this path.

**Not fixed — audit-only mode.**

## RISK-850-253 — CharacterMobs persisted stage-byte vector can overrun the current fixed stage array after content/version shrinkage

Tier: **L3 — Persistence compatibility risk**  
Status: **STATIC_RISK / STALE-BLOB DEPENDENT**  
Severity: **MEDIUM — login-side monster-book state restoration failure**  
Original source identities: `CharacterMobsTable.java`, `MonsterListReader.java`, `L1PcInstance.java`  
Recovered files: `recovered-src-obf/ao/m.java`, `recovered-src-obf/am/d.java`, `recovered-src-obf/ap/u.java`

### Evidence

The live monster-book stage array `pc.dR()` is initialized to a fixed size derived from the current content set:

`MonsterListReader.maxNumber * 3`.

CharacterMobsTable loads a persisted protobuf byte vector and copies it with a loop bounded only by the persisted vector's length:

`pc.dR()[i] = persisted[i]`.

There is no `min(persisted.length, pc.dR().length)` clamp.

The same-version save path serializes the current `pc.dR()` length, so normal data generated by an unchanged content set remains aligned. The risk appears when older/stale/corrupt persistence contains a longer stage vector than the current content-derived array.

The loader catches the resulting exception internally, allowing login to continue with partially/default-restored monster-book state rather than failing the whole connection.

### Conclusion

This is a real compatibility/robustness gap but not a normal client-controlled runtime bug. Keep as RISK unless a supported content downgrade/migration path proves such stale blobs are expected in production.

## BUG-850-254 — weekly quest reset continues after swallowed bulk-delete failure and can resurrect pre-reset progress after restart

Tier: **L2 — Major**  
Status: **STATIC_HIGH_CONFIDENCE / RESET RAM-DB DIVERGENCE**  
Severity: **HIGH — weekly progression persistence integrity**  
Original source identities: `CurrentTimeReseter.java`, `CharacterMobsWeekTable.java`  
Recovered files: `recovered-src-obf/ba/d.java`, `recovered-src-obf/ao/n.java`

### Evidence

The weekly reset timer performs this sequence:

1. calls `CharacterMobsWeekTable.deleteAll()`;
2. for every online player, replaces `pc.dY()` with a fresh weekly quest set;
3. calls `CharacterMobsWeekTable.insert(pc)`;
4. sends the new state to the player.

The bulk delete helper executes:

`DELETE FROM character_mobs_week`

but catches/logs `SQLException` and returns normally. The timer receives no success/failure signal and proceeds with the reset regardless.

If the bulk delete failed, the old rows still exist. The timer then changes online players' live weekly state to the new reset state and attempts a fresh INSERT for each player. Because `login` is the table PRIMARY KEY, those INSERTs collide with the still-existing rows; those SQL failures are also caught/logged and swallowed.

### Impact

The running server can show a successfully reset weekly state while the database still contains the pre-reset progress. A later logout/restart/login can reload stale weekly progress and effectively undo the reset for affected players.

This is distinct from `BUG-850-252`: 252 covers malformed-row login recovery; 254 covers the scheduled reset path continuing after failed bulk deletion.

### Confidence boundary

The divergence requires a database failure during the weekly bulk delete. No claim is made that an ordinary player can directly trigger that database failure.

**Not fixed — audit-only mode.**

## BUG-850-255 — first-row INSERT failure leaves several progress systems live in RAM while logout UPDATEs a row that still does not exist

Tier: **L2 — Major**  
Status: **STATIC_HIGH_CONFIDENCE / INITIALIZATION-PERSISTENCE CONTRACT FAILURE**  
Severity: **HIGH — character progress loss after otherwise normal sessions**  
Original source identities: `CharacterMobsTable.java`, `CharacterMobsWeekTable.java`, `QuestNewTable.java`, `C_LoginToServer.java`, `L1PcInstance.java`  
Recovered files: `recovered-src-obf/ao/m.java`, `recovered-src-obf/ao/n.java`, `recovered-src-obf/ao/az.java`, `recovered-src-obf/aj/bf.java`, `recovered-src-obf/ap/u.java`

### Evidence

Three character-progress subsystems share the same persistence lifecycle:

- `character_mobs`;
- `character_mobs_week`;
- `character_quests_new`.

When no durable row exists, their login/load path attempts a one-time `INSERT`. Each INSERT helper catches/logs SQL failure and returns normally instead of reporting initialization failure to the login flow.

The session nevertheless continues with live state:

- CharacterMobs assigns the new in-memory monster progress array;
- weekly mobs installs a fresh nine-entry weekly set;
- QuestNew proceeds with live quest state populated from the current content definitions.

At normal logout, the corresponding save paths issue plain `UPDATE ... WHERE <key>=?` statements. They do not use upsert/replace behavior and do not check the affected-row count.

If the first INSERT never created the row, the later UPDATE affects zero rows. That zero-row result is treated as success and no INSERT retry occurs.

### Impact

A transient DB failure during first-time initialization can leave a full gameplay session's monster-book, weekly-mob, or new-quest progress in RAM with no durable backing row. Normal logout does not repair the missing-row condition, so reconnect/restart can reconstruct default/current-content state instead of the session's progress.

This is distinct from `BUG-850-252`, which covers a malformed row that already exists and blocks fallback INSERT with a primary-key collision. Here the defect is the opposite state: the row never existed because its initial INSERT failed.

### Confidence boundary

The defect requires a persistence failure during first-row creation. No claim is made that an ordinary client can directly force the database failure.

**Not fixed — audit-only mode.**
