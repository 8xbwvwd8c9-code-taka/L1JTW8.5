## BUG-850-003 — packet header EOF validation checks only the second header byte

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **MEDIUM**  
Original source identity: `ClientThread.java`  
Recovered file: `recovered-src-obf/bj/d.java`

### Evidence

Packet receive code performs:

1. `hiByte = input.read()`
2. `loByte = input.read()`
3. checks only `loByte < 0`
4. calculates packet length using both values.

There is no matching `hiByte < 0` check before the length calculation.

### Impact

A connection closing between the first and second stage of header processing can enter length calculation with an invalid first-byte value. Exact runtime effect depends on socket timing and the second read result.

### Confidence note

This is a source-level boundary defect visible in the recovered method, but it has not yet been reproduced from the supplied runtime logs.

**Not fixed.**

## BUG-850-005 — login password block count is trusted before indexing a fixed 128-byte buffer

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH for connection robustness**  
Original source identity: `C_Login.java`  
Recovered file: `recovered-src-obf/aj/be.java`

### Evidence

The login handler:

- reads a client-controlled `pwLenth`;
- decrypts a fixed 128-byte password block;
- later indexes it as `pw[(i << 2) + j]` while iterating up to `pwLenth`.

No local range check constrains `pwLenth` to the number of 4-byte words available in the 128-byte buffer before those accesses.

### Impact

A malformed login packet can drive array indexing outside the decrypted password buffer. Because the packet constructor is invoked from the packet-dispatch / ClientThread path, the resulting exception can terminate that connection.

### Confidence note

The exact malformed packet has not been replayed in the supplied runtime logs, but the fixed-size buffer and unchecked loop bound are directly visible in the recovered source.

**Not fixed.**

## BUG-850-008 — movement heading is used directly as an 8-entry direction-table index

Severity: **MEDIUM for malformed movement packets**  
Original source identity: `C_MoveChar.java`

- `DIR[heading][0]`

## BUG-850-009 — CraftListTable overwrites first query resources without closing them

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **LOW / MEDIUM resource leak**  
Original source identity: `CraftListTable.java`  
Recovered file: `recovered-src-obf/ao/s.java`

### Evidence

The constructor:

1. opens a connection / statement / result set for `SELECT * FROM craft`;
2. completes that loop;
3. assigns a new connection, statement and result set for `SELECT * FROM craft_exchange`;
4. closes only the resource variables currently referenced at the end.

There is no close between query 1 and the reassignment for query 2.

### Impact

The first query's JDBC resources can remain open after successful table initialization. Because this is singleton initialization, the leak is bounded per initialization, but it still consumes pooled DB resources unnecessarily.

**Not fixed.**

## BUG-850-010 — one malformed craft row can abort loading all remaining craft definitions

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH for content availability / startup correctness**  
Original source identity: `CraftListTable.java`  
Recovered files: `recovered-src-obf/ao/s.java`, `recovered-src-obf/aq/k.java`

### Evidence

Per-field list mismatch catches only `ArrayIndexOutOfBoundsException`, while numeric parsing and item resolution can throw other exceptions such as `NumberFormatException` or null dereferences.

The whole constructor is wrapped by one outer `catch (Exception)`. If any uncaught row-level exception occurs, the constructor logs it and exits the remaining load sequence instead of continuing with later rows.

### Impact

A single malformed craft record can leave the singleton with a partially populated craft map. Depending on where failure occurs, later recipes and/or exchange definitions are unavailable until restart/data correction.

### Related invariant

`L1Craft` also assumes at least one valid output item in several methods via `craftItems.get(0)`; malformed/empty recipe definitions therefore remain a downstream crash risk.

**Not fixed.**

## RISK-850-013 — castle withdrawal is an unsynchronized read-modify-write path

## BUG-850-014 — ShopWorld accepts negative purchase quantity/price and can increase account shop currency

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **CRITICAL — account currency integrity**  
Original source identity: `C_ShopWorld.java`  
Recovered files: `recovered-src-obf/aj/cd.java`, `recovered-src-obf/ao/bd.java`

### Evidence

The purchase path reads client-controlled `count` and `price` and validates only:

`price == unitPrice * count`

There is no `count > 0` or `price > 0` gate.

The balance update is equivalent to:

`accountBalance = accountBalance - price`

Therefore a negative count paired with the matching negative computed price causes subtraction of a negative value and increases the account balance.

The item delivery loop in `ShopWorldTable` executes while `created < count`; for a negative count it creates no items.

### Impact

A malformed purchase request can increase the account's ShopWorld/store currency without consuming a product.

**Not fixed.**

## BUG-850-015 — ShopWorld price validation uses overflow-prone 32-bit multiplication

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **HIGH — economic integrity / malformed packet handling**  
Original source identity: `C_ShopWorld.java`  
Recovered file: `recovered-src-obf/aj/cd.java`

### Evidence

Expected price is calculated as an `int` multiplication:

`shopData.price * count`

before comparison with the client-supplied `price`.

There is no widening to `long` and no overflow check before the balance mutation.

### Impact

Large client-controlled counts can overflow the expected purchase total into an unrelated or negative 32-bit value. If the client supplies that wrapped value, the equality check can still pass and subsequent balance arithmetic can become incorrect.

### Relationship

This is independent of the simple negative-count path in BUG-850-014; both affect the same purchase handler.

**Not fixed.**

## BUG-850-017 — death item-loss path indexes inventory zero when the inventory is empty

Status: **STATIC_HIGH_CONFIDENCE**  
Severity: **MEDIUM — death processing stability**  
Original source identities: `L1PcInstance.java`, `L1PcInventory.java`  
Recovered files: `recovered-src-obf/ap/u.java`, `recovered-src-obf/au/g.java`, `recovered-src-obf/bi/i.java`

### Evidence

Death penalty processing calls the inventory random-loss selector.

The selector performs:

1. `rnd = RandomUtil.nextInt(inventory.size())`
2. `inventory.get(rnd)`

The recovered random helper explicitly returns `0` when its bound is zero.

Therefore an empty inventory produces `get(0)` on an empty list.

### Impact

If an empty-inventory player reaches the item-loss branch during death processing, the scheduled death task can throw an index exception instead of completing the penalty path normally.

**Not fixed.**

## RISK-850-018 — warehouse loaders do not consistently tolerate stale/unknown item ids

Status: **STATIC_RISK**

Recovered files: `recovered-src-obf/au/a.java`, `recovered-src-obf/au/b.java`, `recovered-src-obf/au/c.java`

### Evidence

Warehouse rows resolve `item_id` through `ItemTable`.

The character inventory loader separately detects an unknown template and skips the row, but warehouse loaders do not consistently apply that recovery behavior before constructing an item object. The clan loader explicitly throws when the template is absent.

### Impact

### Confidence note
