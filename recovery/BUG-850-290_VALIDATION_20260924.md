## Audit finding

The original clan-watch add/remove flow persisted the two sides of a bilateral watch relation through independent clan updates. A failure on only one side could leave `clan_data.watch_clanid` asymmetric while SQL errors were not propagated back as one transaction result.

## Validated work repair

```text

WORK_CLOSE_COMMIT=10ace4094d1e89f84480d82ef3535b59803e0e42

WORK_CI_RESULT=PASS
PROOF=SOURCE_CONTRACT_PASS; EXACT_PATCH_NO_NEW_JAVAC_REGRESSION_PASS; TARGETED_RUNTIME_PASS
```

The repair routes both add and remove through `updateWatchRelationAtomic`:

- locks the two clan rows with `SELECT ... FOR UPDATE` in deterministic clan-id order;
- requires `clan_data` to use InnoDB;
- stages both `watch_clanid` sets;
- updates both rows inside one JDBC transaction;
- requires each changed row update to affect exactly one row;
- rolls back on either-side failure;
- publishes both clans' RAM watch sets only after commit;
- converges asymmetric legacy state on a successful add/remove.

No additional BUG-850-290 schema migration is required.
